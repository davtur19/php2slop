# Technical report: real WordPress session decode to zif_passthru

## 1. Objective

Turn the proven session file overread into a real target chain on WordPress plus WooCommerce plus HexCoupon with ASLR on, then call `zif_passthru` through a fake `execute_data` and keep the FPM worker alive.

## 2. Target and stack

The target binary is `/tmp/opencode/realapps/install_realapps_np/sbin/php-fpm`, md5 `4ee099823b75e16ea36f93c71d57bfd8`. The private stack is `/tmp/opencode/research/realchain_20261022T015900Z`, served on `127.0.0.1:28893`. The FPM master is `160462`; the final worker is `169841`.

The application is the real WordPress tree copied from the private HexCoupon lab. The HexCoupon plugin method `LoyaltyProgramHelpers::start_session()` calls `session_start()` at line 85. The pool sets `session.save_path` to the web served `wp-content/uploads/sessions` directory. Nginx serves that directory statically. The attacker controls `PHPSESSID`.

## 3. Primitive

The plant is a 64,946 byte session record consisting of `x|` followed by 7,216 copies of `a:1:{i:0;`. The plant endpoint calls the real plugin `start_session()` with `memory_limit=2M`. The session decode OOMs at plugin line 85 after PHP has set `basic_globals.unserialize` to level 1 with `data=P`. The worker survives because the OOM occurs after RINIT.

The trigger is a multipart POST with `PHP_SESSION_UPLOAD_PROGRESS`. PHP performs a pre RINIT session decode before WordPress loads. That decode uses the stale `basic_globals.unserialize` left by the plant. The trigger session record contains a fake `php_unserialize_data` at `P`, including a fake dtor entry at `P+0x88`. The first variable slot is redirected to `S` or to `ps_serializers[1].decode`. The second decode occurs at progress END and uses the poisoned serializer.

The leak record uses total `0x40000`, first decode buffer `X'=0x7f3d4406a000`, `P=0x7f3d440a0000`, `S=0x7f3d44056080`, and fake dtor `used=-0x4A01`. It writes the `S` field over `S`, making the string length 4096. The second decode at `K_dest=0x7f3d440ab000` writes a 266,522 byte session file. The served file contains `K_dest` at `S` data offset 8 and is fetched over HTTP with an identical hash.

The final record uses total `0x40000`, `P=0x7f3d44097000`, `X=0x7f3d4406a000`, and the leak `K_dest=0x7f3d440ab000`. The final second decode buffer is `0x7f3d440b2000`, value `0x7f3d440b2018`. The fake frame is the first key at the second buffer start. Its `F` field is `0x7f3d440b2218`, which points to the fake zend string at file offset `0x200`. The fake frame sets `num_args=1`, `arg1=F`, and `type=6`. `zif_passthru` reads the command at `F+0x18`.

The static target is `ps_serializers[1].decode=0x22c54c8`. The fake dtor is at `P+0x88`, and the first variable value is decimal `10731636` (`0xa3c074`). The first decode writes `0xa3c074` to `0x22c54c8`. The second decode calls `zif_passthru`.

## 5. Evidence

The gdb verification log shows the first decode with `bgd=0x7f3d44097000`, the static write, the second decode at `0x7f3d440b2000`, `ZIF_PASSTHRU`, and `POPEN` with the marker command. The static poison from that verification was cleared by terminating the prior child; master `160462` persisted and respawned `169841`. This reset is a lab action, not part of the exploit. The final no gdb request produced the marker and preserved worker `169841`. A static session file fetch returned HTTP 200 with 266,522 bytes. A no session PHP endpoint returned HTTP 200 with `ML=2M` and the uploads session path.

The final exploit POST itself returned HTTP 500 with an empty body after the marker. This is the post exploitation shutdown path. The worker survived and served the no session health request afterward. The static serializer remains poisoned at `0x22c54c8`, so session starting endpoints are unsafe after the marker.

## 6. Obstacles and limits

The plant P varied by page across requests on the same master (`0x7f3d44097000`, `0x7f3d440a0000`, `0x7f3d440a2000`). The final record must be rebuilt after the plant measurement. The fake frame `F` must point at the actual second decode buffer, not at the leak `K_dest`; in the real app the final second buffer was `K_dest+0x7000`. The earlier failed attempt used `F=K_dest+0x218` and crashed at `rip=0xb9d576`.

The leak trigger crashes the worker after writing the session file. The FPM master persists, so the file and heap base remain usable. The final request must be the next multipart request after the plant, with no intervening session request.

The lab seeds the session file into the web served writable uploads directory. A real deployment needs an arbitrary file write or upload into that directory and a known `PHPSESSID`, which is the stated precondition. No other server side primitive is required after that write.

The static poison persists in the worker. A session starting health check will call the poisoned decode with normal arguments and can terminate the worker. Use a static file fetch or a no session PHP endpoint for health.
