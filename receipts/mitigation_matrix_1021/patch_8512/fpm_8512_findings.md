# FPM same-worker lane — CVE-2026-109618/109619 verification on PHP 8.5.12

Date: 2026-10-21 (evening).  Work dir: `/tmp/opencode/fpmtest8512_2140/` (fresh, private).
Loopback only.  No other lab directory was written to; `/tmp/opencode/vulntest8512_2127/records/*.sess`
was read (copied into this dir) as the planted stored-record input, and the 8.5.10 control
binary was read from `/home/davide/ailocal/php/zerodays_1020/install_plain/sbin/php-fpm`.

## TL;DR

| question | measured answer |
|---|---|
| (a) Does the php-fpm worker survive the 8.5.12 producer OOM? | **No.** 5/5 producers: the child is gone (`exited with code 70`, `FPM_EXIT_SOFTWARE`) and the master spawns a replacement before the next request.  Same on 8.5.10 (5/5, code 70). |
| (b) Is stale/corrupted global state consumed by the same worker afterwards? | **No — there is no same worker to consume it.**  Every post-producer consumer ran on a freshly spawned child and returned byte-identical baseline bodies.  The only durable effect is **session-record destruction** (data loss) observable by the next worker as `S:0`. |
| (c) Comparison with 8.5.10 | Same worker-exit behaviour and same clean consumer bytes.  Differences: OOM allocation 2,097,152 B vs 266,240 B; 8.5.12 destroys even a small valid session record (8.5.10 keeps a 330 B partial progress record); the 8.5.10 stored-record producer additionally prints `Failed to decode session object. Session has been destroyed`; hard-limit variant on 8.5.12 `_exit(137)` + connection reset. |
| CVE-surviving signal on 8.5.12? | **No.** Decisive evidence: `WARNING: [pool lab] child 1049353 exited with code 70 after 0.138918 seconds from start`, and the next same-sid consumer (new child 1049371) returned `S:1` = baseline `de34ad408f98`, with no warnings. |

## 8. Hard-limit route (`memory_hard_limit_percent=100`)

`Zend/zend_alloc.c:483-521`: when the hard limit is crossed, PHP prints
`Hard memory limit of N bytes exhausted (tried to allocate M bytes) …` to stderr and calls `_exit(137)`.

Observed (×5, 8.5.12): client gets a **connection reset with 0 B** (no END_REQUEST, no headers),
FPM log:

```
WARNING: [pool lab] child 1049717 said into stderr: "Hard memory limit of 8388608 bytes exhausted (tried to allocate 2097152 bytes) in Unknown on line 0"
WARNING: [pool lab] child 1049717 exited with code 137 after 0.130468 seconds from start
NOTICE: [pool lab] child 1049734 started
```

Consumers afterwards are byte-identical to baseline; the 330 B progress record survives.
This is a cleaner hard-kill (no session teardown) than the soft-OOM `exit(70)` path.

## 10. Verdict

**(a) Does the FPM worker survive the 8.5.12 producer OOM?  No.**
Every one of the five producers was served by a child that then exited with code 70
(`FPM_EXIT_SOFTWARE`): `child 1049353 exited with code 70 after 0.138918 seconds from start`,
then `child 1049371 started`.  The producer request left no access-log entry (37 accepted
connections − 32 logged = the 5 producers), i.e. it failed during request startup before script
execution, consistent with the `Unknown on line 0` fatal.  The response nevertheless reaches the
client as **200 + the fatal body** (stdout sha12 `c991c92909c8`, byte-identical to the CGI lane).
The 8.5.10 control behaves the same way (5/5 code 70), so worker replacement is not a 8.5.12
regression — it is the normal FPM reaction to a failed `php_request_startup()`.

**(b) Is any stale/corrupted global state consumed by the same worker afterwards?  No — the
same-worker consumption path does not exist in this arm.**
Because the producer kills the child, every consumer request ran on a *fresh* worker (pid tables
in §5) and returned byte-identical baseline bytes: consumer A `de34ad408f98` (`S:1`) and probe
`b4387566fe80`/`7e3a89c773f7` in all rounds, with no warnings, no corruption and no wedge.
The only persistent effect is the **destruction of the session record** on 8.5.12, seen by the next
worker as `S:0|K:` before a new record is written; the new record is structurally valid.
In the one configuration where the worker *does* survive an OOM (post-RINIT `request_parse_body`,
§9), three consecutive OOMs also left the same worker serving byte-identical baseline responses.

**(c) Comparison with 8.5.10.**
* Same: worker exits with code 70 on every producer; consumers on the replacement worker are clean;
  producer response framing is 200 + fatal text; the CGI-lane stdout hashes match exactly.
* Different: 8.5.12's fatal allocation is 2,097,152 B vs 266,240 B on 8.5.10 (the fixed
  soft-limit/delayed-OOM path), and `tried`/stdout sha differ as already documented for CGI
  (`49910aca3542` vs `561043a1e978`).
* Different (state): 8.5.12 destroys the current session record on the OOM abort even when the
  record is a small valid 376 B one (empty-start lane: session dir empty after every producer),
  while 8.5.10 preserves a 330 B partial progress record in the empty-start lane.  With a planted
  4.98 MB stored record, 8.5.10 destroys it **and** emits the `Failed to decode session object.
  Session has been destroyed` warning on the producer response, while 8.5.12 destroys it silently
  and reissues a new `PHPSESSID` (`Set-Cookie: PHPSESSID=f5fb…`).
* Different (hard kill): `memory_hard_limit_percent=100` on 8.5.12 → stderr `Hard memory limit …`
  + `_exit(137)` + client connection reset, session record left intact; there is no equivalent in
  the 8.5.10 lane.

**CVE-surviving signal on 8.5.12: NO.**
Evidence quote:

> `[21-Oct-2026 21:45:19] WARNING: [pool lab] child 1049353 exited with code 70 after 0.138918 seconds from start`
> — followed by consumer step `c1a` on child `1049371`: body `S:1`, sha12 `de34ad408f98`, identical to the no-producer baseline `de34ad408f98`.

## 11. Confidence and limitations

Confidence: **high** for (a) and for the "no same-worker consumption" part of (b):
* deterministic 5/5 in every lane, byte-identical producer and consumer bodies;
* pid evidence from three independent sources (`ps --ppid`, `pm.status_path` full JSON, access-log `%p`);
* accepted-vs-logged arithmetic isolates exactly the 5 producer requests;
* positive control (§4) proves the harness can observe a worker that *does* survive a fatal;
* the 8.5.12 producer stdout hash matches the independent CGI run byte-for-byte.

Limitations:
* `pm=static`, 1 child, FastCGI over loopback directly (no nginx/apache in front), memory limit set
  with `php_admin_value` — the same shape as the lab reference config, not a full web stack.
* `display_errors=1` was used to keep the producer body comparable with the CGI lane; with
  `display_errors=0` the client would get an empty 200 but the worker-exit behaviour is unchanged
  (the exit happens in FPM's startup-failure path, not in the error display).
* The exact reason the 8.5.12 small session record is unlinked (decode/write failure under memory
  pressure → `s_destroy`) is inferred from the observed `Set-Cookie`/new-id behaviour and the
  `php_session_initialize()`/`s_destroy` code path; it was not individually instrumented with gdb.
* The arm is the lab's reproduction shape (20 parts × 262,144 B filenames), not a vendor PoC; results
  apply to this arm + 8 M limit.
* The 8.5.10 `request_parse_body()` hang (§9) is out-of-arm, single observation, low confidence.
* No ASAN build was used for the FPM lanes (per brief, one build only).
