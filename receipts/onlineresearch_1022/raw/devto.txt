                PHP2Shell: Turning a Session Upload-Progress UAF into Unauthenticated RCE (CVE-2026-109618 / CVE-2026-109619)
#
security
#
php
#

#

I published 
PHP2Shell
, a proof-of-concept for two critical PHP vulnerabilities — 
CVE-2026-109618
 and 
CVE-2026-109619
 — that enable a heap use-after-free in 
session.upload_progress
 and, with the right chain, unauthenticated remote code execution.
For security research and authorized testing only.
Repo: 
github.com/syrex1013/php2shell
  Why this matters
PHP’s multipart upload-progress feature (
session.upload_progress
) is enabled by default in many deployments. The bugs sit in 
ext/session/session.c
 and carry a 
CVSS 9.2
 rating. They affect a long range of versions:

If you still run anything at or below those “vulnerable through” lines — especially EOL 8.1 and older — you should treat this as urgent.
  Background: the two CVEs
Both issues are 
heap use-after-free
 bugs in the rfc1867 upload-progress handler.
The handler caches raw 
zval*
 pointers into the session HashTable (
arData
). When a multipart upload stalls longer than 
session.upload_progress.min_freq
 (default 
1 second
), a later 
FILE_DATA
 event re-enters session init and 
frees that HashTable
. The cached pointers then point at freed memory. The next write (storing 
bytes_processed
 via 
ZVAL_LONG
) goes through those stale pointers.
CVE
Stale pointer
CVE-2026-109618
post_bytes_processed
 (session.c ~3292)
CVE-2026-109619
current_file_bytes_processed
 (session.c ~3318)
Simplified flow from the research:
Phase 1
 — POST multipart with 
PHP_SESSION_UPLOAD_PROGRESS
 → rfc1867 callback caches 
zval*
 into 
arData
.
Stall
 — wait longer than 
min_freq
 → 
php_session_initialize()
 / 
php_session_track_init()
 frees the HashTable.
Phase 2
 — send another 
FILE_DATA
 chunk on the same connection → 
ZVAL_LONG
 writes through the stale pointer (
UAF write
).
The vendor fix removes the long-lived 
zval*
 cache and re-derives the target pointer on each write instead of keeping it across the stall window. Credit for the original research goes to 
Ahmed Sultan (0x4148)
 — see also 
jackalsyn.com/posts/php-up-2026.html
. The PHP patch was committed around September 2026 (bugs.php.net).

Successful arming looks like: session status 200, 
bytes_processed
 updated, and confirmation that cached 
zval*
 pointers were written through (stale path reached).
There is also a 
heap spray
 mode (
--spray N
) that prepends dummy file parts sized to exhaust the ZendMM 256-byte bin (matching an 8-entry session HashTable 
arData
), raising the odds that the stale write hits a live allocation rather than a quietly reallocated table.
  RCE chain (
poc.py
)
Against a vulnerable PHP web app, 
poc.py
 tries several stages ordered by reliability:
Session poison + LFI
 — needs something like 
include($_GET[...])
Log poisoning + LFI
 — needs a readable access log via LFI
FastCGI direct (no LFI)
 — php-fpm reachable on common ports (e.g. 9000–9003)
PEAR webshell drop
 — when 
/usr/share/php/pearcmd.php
 is accessible

  Mitigation
Immediate (no patch required):
; php.ini
session.upload_progress.enabled
=
Off
Enter fullscreen mode
Exit fullscreen mode
Proper fix:
 upgrade PHP to the fixed release for your branch — 
8.2.35+
, 
8.3.36+
, 
8.4.27+
, or 
8.5.12+
. EOL branches (≤ 8.1) will not get a backport; plan a version jump.
Also review apps for LFI, exposed php-fpm, and PEAR endpoints — those turn a memory bug into reliable RCE in the PoC chains above.

  Closing
Session upload progress is an easy feature to leave on and forget. These CVEs show how a stall-window UAF in that path becomes a serious RCE story once you combine it with common app or deployment mistakes.
Patch, or turn 
session.upload_progress.enabled
 off until you can. If you want to reproduce the primitive or the chains in a lab you control, start here: 
github.com/syrex1013/php2shell
.
Questions, lab feedback, or hardening notes — open an issue on the repo or find me as 
syrex1013
 on GitHub.
