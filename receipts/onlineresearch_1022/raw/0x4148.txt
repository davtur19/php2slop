PHP2Shell: Inside PHP Upload Progress and the RCE I Couldn’t Reproduce
October 21, 2026
·
16 min read
A PHP application can reject a malicious request perfectly and still be too late. PHP parses parts of the HTTP request in native code 
before
 your application starts running. That is what makes the reported 
PHP2Shell
 vulnerabilities, 
CVE-2026-109618
 and 
CVE-2026-109619
, worth investigating.
I spent time reading the PHP source, building a PHP 8.4.4 lab, and testing the published RCE approach on PHP-FPM and LiteSpeed. I could reach the upload-progress path and observe its session updates. I could not reproduce a crash or command execution. That gap is the interesting part of this story.
#
TL;DR
What is confirmed:
 PHP announced two critical issues rated 
CVSS v4.0 9.2
 each, with a security release scheduled for 
October 21, 2026, at 14:00 UTC
. At the time of this pre-release analysis, PHP had not published the final affected-version matrix or patch-level root causes.
Why the attack surface matters:
 PHP’s 
session.upload_progress
 callback runs during native 
multipart/form-data
 parsing, before application code. A dedicated upload page is not necessarily required for the parser to run.
What I reproduced:
 On PHP 
8.4.4-FPM/Bookworm
 behind nginx, a controlled multipart request activated upload-progress tracking. A second request observed session counters during the upload. Disabling the feature removed that observable behavior.
What I did not reproduce:
 No process crash or RCE in follow-up tests on 
PHP 8.4.4-FPM
 and 
lsphp 8.2.27
, including attempts with the published heap-forging approach and runtime addresses obtained through GDB. Observing a session counter is 
not proof of a use-after-free
.
What to do:
 Identify the PHP build actually serving web traffic, disable 
session.upload_progress
 if unused, restrict unexpected multipart requests where practical, and apply the vendor security update. Temporary mitigations are not a substitute for patching.
#
Why PHP can process a multipart request before your code
The first mistake is assuming that an upload-related PHP bug requires 
/upload.php
 or a vulnerable application feature.
PHP handles 
multipart/form-data
 through its native RFC1867 parser. When a request reaches a PHP handler, the parser processes form fields and file data before the script starts. The built-in session upload-progress extension can receive those parser events and update session records at that point.
HTTP POST multipart/form-data

  nginx / Apache / proxy
          |
          v
      PHP SAPI
          |
          +--> main/rfc1867.c: multipart parser
          |       |
          |       +--> FORM_DATA / FILE_START / FILE_DATA
          |                     |
          |                     +--> ext/session/session.c
          |                           upload-progress callback
          |
          v
     index.php starts
          |
          v
     Framework / routing / validation

before any scripts execute

With

, the entry can disappear once PHP finishes reading the request. Not seeing it in later application code does not mean the callback never ran. A custom session handler registered by userland PHP is likewise too late to affect the earlier progress processing for that request.
None of this proves that 
every PHP endpoint is exploitable
. The affected code must be reachable under the actual SAPI, INI settings, session conditions, and whichever root cause the official patches ultimately establish. It does explain why “we have no upload page” is a poor risk assessment.

zend_hash_str_find()
 returns a 
zval *
 pointing into HashTable-owned storage. Caching the pointer is safe only while that particular slot remains valid. A PHP array value being alive and a pointer to one of its internal slots remaining valid are 
not automatically the same guarantee
.
When file data arrives, PHP 8.4.4 writes the counters and then invokes the periodic update:
Z_LVAL_P(progress->current_file_bytes_processed) =
    data->offset + data->length;
Z_LVAL_P(progress->post_bytes_processed) =
    data->post_bytes_processed;
php_session_rfc1867_update(progress, 
0
);

(

These are the actual 
Z_LVAL_P
 assignments
 in the version I reviewed, not the 
ZVAL_LONG
 calls that appeared in an earlier description of the bug.
The update path can reinitialize the session and write the progress record back:
/* Selected operations in php_session_rfc1867_update();
   intervening conditions omitted. */
php_session_initialize();
PS(session_status) = php_session_active;
Z_TRY_ADDREF(progress->data);
zend_hash_update(Z_ARRVAL_P(sess_var), progress->key.s, &progress->data);
php_session_flush(
1
);
Code language:
Arduino
(
arduino

Session initialization can also destroy previous session-state values through 
php_session_track_init()
 and 
zval_ptr_dtor(&PS(http_session_vars))
.
Here is the memory-ownership question: 
does that process actually release the 
arData
 allocation containing one of the cached counters?
 If it does, a later 
FILE_DATA
 event may write through a dangling pointer. If it only frees a separate decoded session array, the proposed use-after-free explanation is incomplete. 
Z_TRY_ADDREF(progress->data)
, array separation, and reference counts all matter.
The event order matters too. The first 
FILE_DATA
 event 
writes before calling
php_session_rfc1867_update()
. If that update invalidates a pointer, the interesting stale write would occur on a 
subsequent
 data event, not on the write that preceded the update.
FILE_START      Cache counter zval* addresses
    |
FILE_DATA       Write counters while slots are valid
    |
update()        Reinitialize / replace session state
    |           Does the *same* owning allocation get freed?
    v
next FILE_DATA  Reuse cached pointers
                Potential UAF only if their storage died
Code language:
plaintext
(
plaintext
)
That last condition is where a source-level suspicion becomes a memory-safety finding. Seeing 
php_session_initialize()
 run is not enough. I would need to record the cached pointer, its owner, the precise free, and the later access to the same address. The original public analysis proposes such a path; my own lab has not supplied that allocation trace.

#
I tried the published RCE chain. It did not reproduce.
The 
PHP-UP-2026 publication
 describes more than a callback bug. It ships a framework (
php_up_framework.py
) and separate PoCs for the two CVEs. The proposed chain uses a cached pointer, session-state changes, and heap allocations designed to reclaim the freed space with forged Zend callable structures. The reported endpoint is 
zend_call_function()
 and ultimately command execution.
That claim is testable, which I appreciate. I tested its approach on my builds instead of taking “RCE” in the title as the last word.

Upload-progress path reached; no worker crash or RCE

These are negative results for 
my tested configurations
, not proof that exploitation is impossible on the original author’s exact binary. I also did not independently capture a conclusive stale-pointer sanitizer trace.
#
The ownership question comes first
The published explanation describes session reinitialization freeing an older tree. But the cached counters are obtained from 
progress->data
 and 
progress->current_file
. Those are not automatically the same allocation as the old decoded session root. The refcount adjustments and any copy-on-write separation need to be followed through the update path.
If the exact 
arData
 block backing a cached counter never gets freed, there is nothing for a heap spray to reclaim. This is a more basic question than the number of objects in a spray. My source review identified it as unresolved, not disproved.
#
A size match is not a heap overlap
The publication’s forge technique describes 
149 multipart parameters
 carrying 
288-byte data
 intended to reach a ZendMM allocation class around 
320 bytes
. Even if those allocations use the expected size class, they still must land in the 
exact slot
 previously occupied by the allegedly freed HashTable data. ZendMM’s allocator state, free lists, extensions, and request history affect that outcome.
My tests did not record a successful overlap. That could explain failure, but I cannot present allocator placement as the proven blocker without tracing the allocations. Requesting a 320-byte allocation is not a reservation for one particular 320-byte address.
#
A symbol delta is not an ASLR bypass
The original material provides offsets between internal functions for particular 
lsphp82
 builds. Those offsets are build-specific. They do not by themselves reveal the 
runtime address
 needed to use forged function pointers under ASLR.
The public framework accepts a 
--dtor <leak>
 input, which assumes that a function address has already been obtained. The disclosure does not demonstrate a generally available unauthenticated information leak that supplies it.
For my local tests I supplied GDB-derived runtime addresses to remove that uncertainty. The chain still failed. That tells me 
ASLR alone did not explain my failures
; it does not provide a remote ASLR bypass.
One correction worth preserving: 
PHP 8.2.34 was released September 24, 2026
, according to 
PHP’s changelog
. Its release did not happen on the October 21 disclosure day. I could not reproduce the published result on my available 
lsphp
 build, but that is not evidence that its target package never existed.
#
What a working RCE claim still needs
An effective chain would need to establish the actual free and later stale access, reclamation of the correct allocation, corruption of bytes that are subsequently interpreted as a callable, and suitable runtime addresses. A sanitizer report can establish a memory bug, but 
a sanitizer report is not an end-to-end RCE demonstration
.
I did not find a reproducible successful execution trace on the publication page, and my tests did not produce one. That is a reason to describe the RCE as 
not independently reproduced here
, rather than to accuse the original author of fabricating results. An absence of public evidence is not proof an exploit never worked.
The proposed CVE-to-pointer mapping, one for the outer counter and one for the per-file counter, likewise remains a 
public research attribution
, not a vendor-confirmed split in this pre-release article.
#

#
Detection: useful leads, not magic signatures
A request using 
PHP_SESSION_UPLOAD_PROGRESS
 is not automatically malicious; it is a documented feature. Neither is 
multipart/form-data
 a reliable indicator by itself. I would correlate 
unexpected multipart requests on non-upload routes
 with unusual request duration, PHP worker crashes or restarts, and process activity under the web-server account. Unexpected shells, outbound connections, or file changes deserve separate investigation.
Most access logs do not include multipart body fields. If a WAF has request metadata, preserve it without unnecessarily retaining session IDs or uploaded contents. A missing string in an ordinary access log does not clear the host.
A patched runtime also does not undo any persistence or credential exposure from a previous compromise. If exploitation is suspected, preserve evidence and investigate the host separately.
#
Final conclusion
The most useful part of PHP2Shell is the boundary it exposes: 
native PHP request processing happens before application validation
. That behavior is documented, and my PHP 8.4.4 lab confirmed that the upload-progress mechanism can be reached and observed during a multipart request.
The stronger claim is where I remain unconvinced. I could trace the cached 
zval *
 lookups and counter writes in source, and I tested the published RCE approach across PHP-FPM and LiteSpeed builds. 
I could not reproduce a crash, a proven freed-slot write, or code execution.
 The outstanding question is whether session reinitialization frees the 
specific
 allocation those pointers reference. Without that evidence, the reported heap-forging chain is not established by my results.
That does not make the announced PHP vulnerabilities safe to ignore. Disable upload progress if you do not use it, verify the actual web-facing PHP configuration, and patch as soon as the official releases are available. I would rather have a reproducible crash trace than a very impressive “RCE achieved” label attached to a request that completed normally.
